# 1UP Auth — implementación y activación

Estado: código para revisión; configuración pública desactivada (`ONEUP_AUTH_CONFIG=null`). No hay proyecto Supabase conectado ni credenciales SMTP, y no se ha comprobado entrega de correo real. No fusionar como un servicio ya operativo. Pages sirve solamente el frontend; la función se despliega aparte.

## Arquitectura y costo

GitHub Pages → Edge Function `oneup-auth` → Supabase Auth/Postgres → Resend por SMTP. Supabase genera y consume OTP, almacena hashes de contraseñas y valida las credenciales. El broker no implementa criptografía de contraseñas. Postgres reserva nombres únicos, controla límites atómicos y guarda sesiones opacas. El cliente no necesita claves Supabase: solo URL del broker y clave **pública** Turnstile. Nunca colocar service role, SMTP, token Management API ni secreto de sesiones en archivos públicos, Actions logs o conversaciones.

Según [Supabase Free](https://supabase.com/pricing), incluye 50.000 usuarios activos/mes, 500 MB de base y pausa tras una semana inactivo; no es SLA de producción. [Resend Free](https://resend.com/pricing) permite 3.000 mensajes/mes y 100/día: el broker limita a 90/24h y 2.700/31 días, además del límite nativo de 30/h. Estos límites no incluyen correos enviados por otras aplicaciones ni accesos directos a Auth; usar un proyecto/remitente dedicado y vigilar cuotas. La capa gratuita es viable para una comunidad pequeña, no para crecimiento ilimitado. El dominio de envío debe pertenecer al titular: si no tiene uno con DNS editable, adquirirlo puede costar dinero. El dominio compartido `github.io` no puede verificarse como remitente propio. No se compra ni activa facturación automáticamente.

## Controles y límites exactos

- Usuario: 3–24 letras ASCII, números o `_`, normalizado a minúsculas. Reserva única al crear `auth.users`; no se confía en metadata editable para autorizar ni cambiar el nombre canónico. No se publican directorios de nombres/correos. Un nombre reservado por un registro sin completar requiere recuperación por correo o revisión del titular; no se purgan cuentas automáticamente.
- Contraseña: 15 caracteres mínimo, máximo 72 **bytes** por compatibilidad bcrypt, sin truncar; rechaza repeticiones triviales y algunas cadenas comunes. Se admiten frases y pegado de gestor. No es una lista exhaustiva de contraseñas filtradas. Política nativa mínima de 15 obligatoria también ante accesos directos a Supabase.
- OTP: exactamente 6 dígitos. Caducidad/uso único son controles de **Supabase**, necesitan configuración y prueba real. Broker: 5 verificaciones por correo/10 min compartidas por alta/recuperación y reenvíos; reenviar no restablece el presupuesto. Login: 10 intentos/nombre/15 min. Correo: 1/min y 3/h por dirección. Contador global de 500 solicitudes/min protege presupuesto; puede causar indisponibilidad bajo ataque y no sustituye WAF. Límites persistentes con UPSERT atómico, HMAC de sujetos para no guardar correos en contadores. Respuestas de envío genéricas también ante cuentas existentes y colisiones; no prometen que el proveedor entregó un mensaje. No se promete anonimato temporal perfecto del login.
- Sesión de aplicación: bearer aleatorio de 256 bits en memoria del navegador; únicamente SHA-256 en base. Token nativo cifrado AES-GCM con IV aleatorio y secreto del servidor. No se envían tokens nativos ni refresh tokens al navegador. Expira como máximo al token nativo (600 s configurados) o 1 h; no hay renovación silenciosa ni persistencia al recargar. La función verifica usuario confirmado, alcance, expiración y existencia de `session_id` en `auth.sessions` (edad máxima 1 h) tras validar JWT con Auth. Cerrar sesión revoca todas las sesiones de 1UP y las nativas de ese usuario. Una falla de red puede impedir revocación remota: el cliente borra su token y el servidor mantiene la expiración corta; verificar cierre remoto en E2E.
- Recuperación: OTP nativo tipo `recovery`; entrega un bearer distinto con alcance exclusivo de cambio de contraseña y TTL de 5 min. DELETE con `return=representation` lo consume atómicamente **antes** del cambio. Una falla posterior exige solicitar otro código; no reutilizar automáticamente. Cambiar contraseña revoca todas las sesiones 1UP y nativas; la respuesta indica el nombre de usuario al titular que ya demostró posesión del correo. Alcance `access` no puede cambiar contraseña en este broker.
- RLS y privilegios: las tres tablas están cerradas a anon/authenticated; solo service role accede. RPC invocables solo por service role. Funciones que necesitan leer `auth.sessions` o trigger están en schema privado, `search_path=''`. No hay roles, favoritos ni datos de comunidad autorizados mediante eventos JS, localStorage o `user_metadata`. Solo una futura API de negocio que valide la sesión broker podrá consumirla.
- CORS compara origen exacto; no autentica clientes no navegador. JSON máx. 4 KiB leído por stream, métodos/acciones explícitos, respuestas no-store, errores sin detalles internos. Esta entrega no elimina el riesgo XSS del sitio: cualquier script con ejecución en la página podría capturar credenciales o la sesión en memoria. Mantener dependencias/CSP de la web bajo revisión.
